# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TeamClaude is a transparent HTTP proxy that sits between Claude Code and the Anthropic API, managing multiple Claude (Max/Pro/API-key) accounts and rotating between them when one nears its session (5h) or weekly (7d) quota. Published as `@karpeleslab/teamclaude`.

## Commands

There is **no build step**. Development is run directly against source.

```bash
node src/index.js <command>        # run any CLI command locally (server is the default)
node src/index.js stop             # stop the running server (restart = stop + start)
npm start                          # = node src/index.js (starts the proxy server)
npm test                           # = node --test  (tests live in test/)
npm run lint                       # = eslint .  (flat config in eslint.config.js; lints test/ too, not just src/)

# Use a throwaway config instead of ~/.config/teamclaude.json:
TEAMCLAUDE_CONFIG=./config.json node src/index.js server
```

`config.json` is gitignored; `config.example.json` is the template. To exercise the proxy end-to-end, start `server` in one terminal and `node src/index.js run` (or `eval $(node src/index.js env)` then `claude`) in another.

## Hard constraints (do not break these)

- **Zero runtime dependencies.** This is an advertised feature — use only Node.js built-in modules. Do not add anything to `dependencies`.
- **ES modules, Node 18+.** `"type": "module"`, top-level `await` is used in `src/index.js`.
- **ESLint globals are explicitly enumerated** in `eslint.config.js`. If you use a new global (a timer, a Web API like `crypto`/`TextEncoder`), add it to the `globals` map or `no-undef` will error.

## Architecture

Single CLI binary (`src/index.js`) dispatches subcommands; `server` boots the proxy. `src/` is ~26 modules (`ls src/*.js`); the load-bearing layers are below (not exhaustive — the rest are focused subsystems: identity keys, MITM/x509 CONNECT, sx egress proxy, model/route matching, session tracking, request logging, status rendering, self-update):

- **`src/index.js`** — CLI dispatcher + all non-server commands (`stop`, `restart`, `import`, `login`, `env`, `status`, `accounts`, `remove`, `api`). Owns the **config-sync wiring** between the running server, the TUI, and external CLI invocations (see below), and the **server-lifecycle helpers** (`findRunningServer`/`stopRunningServer` — discover a running proxy via the state file `getServerStatePath()`, falling back to a port probe + `lsof`, then SIGTERM→SIGKILL it; `server` writes the state file on listen and removes it on exit).
- **`src/server.js`** — the HTTP proxy and the request-forwarding loop (`forwardRequest`), including account acquisition (concurrency slot), retry, rate-limit handling, SSE streaming, and optional request logging.
- **`src/account-manager.js`** — `AccountManager` class: in-memory account state, use-or-lose selection, **per-account concurrency cap + overflow queue** (`acquireAccount`/`releaseAccount`), quota tracking from response headers, and token-refresh coalescing. The single source of truth for *live* credentials while the server runs.
- **`src/oauth.js`** — OAuth PKCE login, token refresh, profile fetch, and credential import from Claude Code. No proxy state here — pure functions.
- **`src/config.js`** — load/save of `~/.config/teamclaude.json` (override via `TEAMCLAUDE_CONFIG`, or `$XDG_CONFIG_HOME`). Written `0o600`.
- **`src/tui.js`** — full-screen terminal dashboard (alternate screen buffer). Only used when both stdin and stdout are TTYs; otherwise the server logs plainly.
- **`src/maintenance-coordinator.js`** — the sole timer owner for background maintenance (active warm-up, quota probe, keep-warm): scheduling, abort, per-account serialization, capacity admission. Add a periodic job via `maintenance.schedule(name, ms, fn, { immediate })`, never a bare `setInterval` — `immediate` defaults to false and `reschedule`'s `!wasOn` default **cannot fire at startup** (the constructor already set `intervalMs`), so a job that must not be blind for its first interval passes it explicitly. **Then decide which side of the admission gate it is on.** Plain `run(account, kind, priority, task)` executes only if `acquireAccount` grants that pinned account a slot, so a disabled/throttled/parked/over-threshold/capped account silently never runs it. `run(..., { zeroSpend: true })` declares the task sends no `/v1/messages` (today only the `/api/oauth/usage` read): it still takes a free slot — `inflight` never exceeds `maxConcurrent` — but runs when refused one, needing only a live account. Spending work stays gated; a read must not be, since the accounts whose quota is otherwise unreadable are exactly the ones the gate refuses (measured: 0 of 6 probed in 30 min).
- **`src/prober.js` / `src/warmer.js`** — three confusable warm-up-ish mechanisms live in three places: the capture-replay **active warm-up** (server.js, below) measures quota by replaying the accepted template; the **prober** reads quota zero-spend from the OAuth usage endpoint (`config.quotaProbeSeconds`); the **warmer** *spends* a minimal message per idle account to start its 5h session timer (`config.warmupSeconds`). Edit the right one.

### Request flow (`forwardRequest` in server.js)

1. localhost clients skip proxy-API-key auth (`isLocal` check); remote clients must send the matching `x-api-key`.
2. `GET /teamclaude/status` returns `AccountManager.getStatus()` (credential-free).
3. **`POST /v1/oauth/token` is relayed untouched** (`relayRaw`) — the client manages its own token lifecycle independently of the proxy's. Never intercept or rewrite it; doing so causes token-rotation conflicts.
4. Body is fully buffered (needed to replay on 429 retry). Hop-by-hop headers, `x-api-key`, and `accept-encoding` are stripped before forwarding (Node `fetch` auto-decompresses, so `content-encoding`/`content-length` are also dropped on the way back).
5. Account acquired via `acquireAccount()` (reserves one of the account's concurrency slots — see Concurrency below); OAuth token refreshed if expiring within 5 min. The slot is released in the request's `finally`; a failover (429/5xx/error) releases the current slot via `releaseHeld()` before recursing onto another account, while a 401 same-account refresh-retry keeps the slot (`ctx.held`). **The rule: an await on the *upstream* (the fetch, a coalesced `ensureTokenFresh`) may hold the slot; an await on the *clock* may not** — see step 7.
6. **429 handling classifies the 429 (`isExhausted`, checked after `updateQuota` folds in the response headers) before acting** — never sleep on `retry-after` holding the client connection:
   - **Account-quota exhaustion** (`anthropic-ratelimit-unified-status: rejected`, or measured utilization ≥ threshold): throttle the account for `retry-after` (clamped to `[1s, 5m]`) and immediately re-dispatch to another available account. When *every* account is throttled, `getActiveAccount` returns `null` and the client gets a `429` to back off itself. This keeps cold-start warm-up fast (an exhausted account is skipped in one round-trip, not a 60s stall).
   - **Non-exhaustion 429** (an account request-rate / concurrency limit — token quota left but hit too fast — or a transient/global limit): fail the request *over* to another available account (per-request exclusion via `ctx.tried429`; `getActiveAccount(exclude)` then picks a different account without disturbing the sticky primary). This spreads the concurrent overflow that use-or-lose otherwise pins onto one account, instead of failing. The account is **not throttled** — throttling on a request-global 429 would poison the fleet for unrelated requests. Only once *every* available account has been tried for this request is the 429 passed through to the client. No account state is mutated either way.

   When the active account crosses `switchThreshold`, the *next* request switches to the highest-priority account (see Account selection below).
7. **Retryable upstream 5xx** (`RETRYABLE_STATUS` = 500/502/503/504/**529 Overloaded**) — passing a 529 through fails the client's whole turn, so it is a three-stage ladder: (a) fail over to an account not yet tried this request (`ctx.tried5xx`); (b) once every *eligible* account has 5xx'd, **release the slot, then sleep** a bounded exponential backoff (`TEAMCLAUDE_OVERLOAD_*` env: base 1000 × 2ⁿ, cap 10000, ≤6 rounds), clear `ctx.tried5xx`, retry the whole fleet; (c) budget spent → pass the status through with a `parseRetryAfter` `retry-after`, else the client SDK falls back to ~0s ("Retrying in 0s") and re-floods an upstream we just measured as overloaded. No account state is mutated — a 529 is upstream overload, not a bad account. **The release in (b) is load-bearing**: a request sleeping with a slot holds capacity on the account everyone else is queued behind, so N concurrent backoffs remove N/`maxConcurrent` of the usable fleet and time waiters out into 429s naming a shortage that does not exist. Logs report how many accounts actually 5xx'd, never "every account" — with the fleet benched to one eligible account that reads as an Anthropic-wide outage.
8. **Transient network errors** (`ECONNRESET`/`ETIMEDOUT`/`fetch failed`) → `res.destroy()` so the client retries; they are not retried internally.
9. All accounts unavailable → `429`. `merelyCapped` (via `anyCapped`) splits the message and the `retry-after`: a busy fleet gets "All N accounts are at their concurrency cap" + `CAPPED_RETRY_AFTER_SECONDS` (1s, shared with the pinned-account branch), a spent one gets "exhausted" + a reset-derived wait. The two need opposite operator responses — reduce concurrency vs add accounts — so they must never share a string.

### Quota tracking (account-manager.js)

Two header families drive rotation, normalized into one model:
- **Unified** (`anthropic-ratelimit-unified-5h/7d-utilization` + `-reset`) — Claude Max/Pro. Utilization is already `0–1`.
- **Standard** (`anthropic-ratelimit-tokens/requests-*`) — API-key accounts; utilization is derived as `1 - remaining/limit`.

**Model-scoped weekly windows** (`anthropic-ratelimit-unified-7d_<label>-*`, currently `7d_oi` — the separate weekly limit for the top model tier, shown as "Fable" in Claude's usage UI) are parsed generically into `quota.modelWeekly` and surfaced in the TUI (third `Fbl` bar on wide terminals) and `teamclaude status`. They are **model-scoped, not display-only**: `_isNearQuota(account, model)` consults `_governingWeekly` — the one weekly bucket that governs *this* request's model — so a spent Fable bucket bars only Fable while Sonnet/Haiku keep routing there (`_modelWeeklyExhausted`; pinned by "a Fable-exhausted account is skipped for Fable but used for other models"). A request with no model carries no model-scoped gate. These headers only appear on responses to requests *for that model tier*, so the value updates only when such traffic flows through the account — which is why the warm-up probe template performs a one-way **upgrade** to a shape whose own response carried a `7d_*` window (see Active warm-up below): without it, a template captured from e.g. a background haiku request could never refresh the Fbl numbers. **Residual limitation** (narrower than it looks — do NOT rebuild per-model routing, it already exists): `classify429` returns `model-quota` whenever the 429 itself carries a binding `7d_*` utilization header, and that branch fails the request over per-request *without* `markRateLimited`/`pauseAccount`, so nothing is throttled globally. Only a Fable 429 that arrives with top-level `unified-status: rejected` **and no** `7d_oi` header falls through to `account-quota` and throttles the account for the clamped `retry-after` (≤5 min), blocking its cross-model traffic for those minutes.

`switchThreshold` (default `0.98`) is the cutoff above which an account is treated as full and skipped. Expired quota windows (including model-scoped ones) are lazily cleared inside `_isNearQuota`.

### Account selection (`getActiveAccount` in account-manager.js)

**Cold-start warm-up first**: quota is only populated after a request flows through an account (`updateQuota`), so `_nextWarmup` round-robins across the still-**unmeasured** available accounts (`_isWarmupTarget`) and `getActiveAccount` routes to them before any priority decision. Warm-up keys on `_isMeasured` (has the account ever returned rate-limit headers?), **not** on "has it made a request" — a response with no rate-limit headers (a `HEAD /`, a 404, an auth failure) must not permanently mark an account measured, or it gets trapped as unmeasured forever (sorted last by use-or-lose, bounced by the rebalance below), never used and never refreshed. `maxWarmupTries` provides the loop-safety: a genuinely dead account (always header-less / 401) is abandoned after a few attempts. An expired-token account resolves on its first warm-up routing — `ensureTokenFresh` refreshes it into a measurable state or marks it `error`. Only once no unmeasured account remains does priority selection run.

Selection is then **use-or-lose**, not round-robin: among accounts under the threshold, `_selectBest` picks the one whose **weekly (7d) quota resets soonest** (`_weeklyResetTime`) — the weekly window is the scarce resource, so an account whose week is about to renew (and whose unspent quota would be wasted) is drained first — tie-broken by **soonest session reset** (`_sessionResetTime`), then **lowest session utilization** (`_sessionUtilization`). Accounts with no weekly data (API-key, or an expired/unmeasured 7d window) rank at `Infinity` and tie, so the session tiebreak reproduces the pre-weekly ordering for them. **Reset rollovers reflect immediately**: a timestamp that has passed also ranks at `Infinity` (`_weeklyResetTime`/`_sessionResetTime` clamp) — otherwise the past timestamp (smallest value) would pin the account at the top of the auto order until a request-path sweep cleared it. The warm-up timer additionally calls `sweepExpired()` every interval so an idle proxy clears rolled-over windows (→ unmeasured → re-probed → fresh order) without needing traffic. The session/utilization helpers fall back from unified (Max) to standard (API-key) metrics.

**Manual controls layered on top (don't change the use-or-lose core when unused):**
- **Disable / enable** (`setDisabled`, config `accounts[].disabled: true`; legacy `enabled: false` still accepted at load, `setEnabled` is a thin wrapper): a disabled account is excluded from rotation by a single gate in `_isAvailable` (which every selection path — warm-up, `_selectBest`, `_cappedSet`, `anyUsable/anyCapped`, the sticky-current check — already funnels through; `_recoverSoonest` skips disabled accounts itself). In-flight requests on a just-disabled account **drain** (the flag doesn't touch `inflight`); re-enabling calls `_drainWaiters()` so its freed capacity is handed to any queued waiter immediately. Surfaced as `status` "disabled" in the TUI (the default view has a **`↑/↓`** selection cursor; **`e`** toggles the selected account directly) and `[disabled]` in `teamclaude status`; CLI `teamclaude disable|enable <name>`. Re-enabling also clears a stuck `error` **regardless of cause** (`setDisabled`) — an explicit operator action is a verified heal, like new credentials; the sweep's refresh-success heals only refresh-caused errors.
- **Explicit priority / order** (`setPriority`, config `priority: <int>`): `_selectBest` sorts by `_priority` **first** (lower number = preferred), then the existing reset/util use-or-lose as tiebreakers. Unset is `null` → `_priority` returns `Infinity`, so **when no account sets a priority every account ties there and the sort falls through to the original use-or-lose unchanged**. In the TUI this is surfaced as an **order**, not a number: the default view has a **`↑/↓`** selection cursor (the action keys — `s` switch, `e` enable/disable, `o` order — act directly on the selected account; only the destructive `d` keeps a confirmation step), and **`o`** grabs the selected account into a move mode where **`↑/↓` reorder** it, **`a` resets the WHOLE order** (clears every rank — the fleet returns to auto weekly-reset ordering), and **`c` clears just the grabbed account's rank** (`_keyNormal` / `_moveOrder` / `_setAutoOrder` / `_applyRanking` in tui.js). Ranked accounts get contiguous priorities `0,1,2,…` and render as `#1 #2 …` (most-preferred first, shown above the rest); moving an unranked account up ranks it at the bottom of the ranked group, moving the last ranked account down un-ranks it back to use-or-lose — so you pin a few accounts and the rest stay on the auto rotation (weekly reset soonest first). The TUI list is sorted by this order (`_displayList`: ranked first, then unranked in their actual auto drain order via `autoCompare` — weekly reset soonest first; ties keep array order since the comparator returns 0 and the sort is stable). A move renumbers to contiguous values, normalizing any legacy/duplicate priority numbers. CLI `teamclaude priority <name> <n|auto|clear>` still accepts raw numbers.
- **Prompt re-pick on change** (`_reprioritize`, called by both setters): a preference change re-picks the active account *directly* and at once — but only when it actually matters, i.e. the current account is no longer usable, or another account is **strictly preferred** by the full order (`_strictlyPrefer`: priority → soonest reset → least used). A no-op (or a change that doesn't dethrone the current) leaves the sticky primary untouched, so it can't churn cache locality, and it does **not** poke `lastEvalAt` (which would wake the periodic tie round-robin). This makes a change take effect immediately even with the re-eval timer off (`reevalIntervalMs <= 0`), and lets clearing a priority restore use-or-lose routing.
- **Interaction with connection affinity (intended):** `_reprioritize` moves the *global* sticky primary, but a live keep-alive connection with an established `_affinity` home keeps routing to that home (cache locality) — exactly as it already does for the periodic `reevalIntervalMs` re-prioritization. So an explicit **priority** change routes **new** connections by the new order immediately, while existing keep-alive connections follow it once their socket closes (or their account caps). **Disable** is different: it's a hard exclusion, and the affinity path requires an *available* home (`_isAvailable`), so a disabled account drops its keep-alive connections on their next acquire too. Set `config.sessionAffinity: false` to route every request purely by priority/use-or-lose with no connection pinning.
- Both fields persist in `config.accounts[]` (survive token-refresh writes and `saveConfig`), and `syncAccountsFromDisk` applies disk changes to the live `AccountManager` on reload (TUI **R** / restart) so a CLI `disable`/`priority` while the server runs takes effect without an edit race.

To balance this against Anthropic's per-account prompt cache (separate per org → switching mid-stream causes cache-miss cost), the active account is **sticky**: priority is only re-evaluated once per `reevalIntervalMs` (default 5 min, `config.reevalIntervalMs`), plus immediately whenever the current account becomes unavailable (over threshold / throttled / error). `lastEvalAt = 0` forces a priority pick on the first request. When all accounts are over threshold, `_recoverSoonest` returns the soonest-to-reset (and `getActiveAccount` returns `null` until then, yielding a `429`).

### Active warm-up (server.js) — populate the whole fleet after a restart

The cold-start warm-up above is **passive**: it only measures an account when a *client* request happens to route there, so on a fresh (re)start the dashboard shows most accounts as "—" until traffic organically reaches each one — Anthropic has **no "get my quota" endpoint**, so quota is only ever learned from real `/v1/messages` rate-limit response headers. **Active warm-up** (`createProxyServer`, gated by `config.activeWarmup` — default on) closes that gap by proactively probing the unmeasured accounts:

- **Capture-and-replay template.** The first genuine `POST /v1/messages` that passes through is snapshotted into `probeTemplate = { model, version, beta, system }` (path-exact, so `/v1/messages/count_tokens` isn't mistaken for inference). Replaying a *known-accepted* shape — the exact model, `anthropic-version`/`anthropic-beta`, and the Claude-Code `system` prompt an OAuth request requires — means a probe can't fail with a guessed-wrong 4xx, and never needs hardcoded model/beta strings that drift. Staging/committing happens **after** the response (the body parse is only paid when a commit is possible), and exactly one one-way **upgrade** is allowed: a shape whose own response carried a model-scoped `7d_*` window (`_elicitsModelWeekly`, tracked via `ctx.sawModelWeekly`) replaces a committed shape that didn't — otherwise probes replaying a lower-tier template could never refresh the Fable weekly numbers. No downgrade: later lower-tier traffic leaves the upgraded template in place.
- **Minimal probe.** `warmupAccount` refreshes the account's token (`ensureTokenFresh`), sends a `max_tokens: 1` `/v1/messages` with that account's own auth header (`Bearer` for OAuth, `x-api-key` otherwise), folds the response's `anthropic-ratelimit-*` headers into `updateQuota`, and cancels the body. It's **best-effort**: any failure just leaves the account unmeasured exactly as before — client traffic is never affected. Probes run **outside** the concurrency-cap accounting on purpose: they only ever target `warmupCandidates()` (available **and** unmeasured), which by definition are *not* the sticky account real traffic concentrates on, so a probe can't collide with a client request on the same account's cap.
- **When it runs.** Once the instant the template is first captured — `setImmediate(warmupUnmeasured)` fans out to every unmeasured account in parallel, so the whole fleet is populated within seconds of the **first** post-restart request (not whenever traffic trickles to each account). Then periodically every `config.warmupIntervalMs` (default 5 min; `0` = startup-only) — which also re-populates an account whose quota window just **reset** (its utilization is cleared, so it reads "—" again). `warmupInFlight` prevents overlapping fan-outs; a per-account `_warming` flag prevents duplicate concurrent probes. The periodic pass is owned by the MaintenanceCoordinator (`maintenance.schedule('active-warmup', …)` in server.js), which coalesces overlapping runs.
- **Limitation:** on a *totally* cold proxy with **zero** traffic there's no template yet, so nothing is probed until the first real request flows — by design, since that first request is what tells us the known-good header shape. `config.activeWarmup: false` disables capture, the startup fan-out, and the periodic timer entirely.
- **Forced fleet re-measure (TUI `R`)**: the plain warm-up only probes accounts that aren't fully measured, so displayed usage drifts silently when quota is spent *outside* this proxy (another device/session). `server.refreshQuotaAll()` (wired to the TUI Reload path after the config sync) probes EVERY idle account — measured, throttled or near-quota included (their exhausted-429 responses still carry authoritative headers), **and disabled accounts too** (out of *rotation*, not *monitoring* — a probe is read-only so it refreshes their dashboard row without re-enabling them) — skipping only in-flight (`inflight > 0`) and auth-error accounts, and renews the convergence budgets first. Returns `{ targets, measured }`, or `-1` when no template has been committed yet (surfaced honestly in the activity log instead of a silent no-op). Deliberately not exposed over HTTP — it spends real upstream requests.
- **Model-weekly (Fable) top-up (`topUpModelWeekly`)**: the `7d_oi` window only appears on Fable-tier responses, so an account measured for 5h/7d by lower-tier traffic keeps a blank `Fbl` bar — and because it's *fully measured*, ordinary warm-up never re-probes it. The periodic timer runs a bounded top-up pass (only once the committed template `_elicitsModelWeekly`) over accounts flagged by `needsModelWeekly` (fully measured, `modelWeekly` empty, under the `_mwProbes` cap), so the Fable numbers self-heal within a warm-up interval; an on-demand `R` heals them immediately. The cap (reset when the window populates or a quota window is swept) stops an account whose upstream genuinely never reports the window from being probed every interval forever.

### Concurrency (per-account cap + overflow queue)

`getActiveAccount` alone funnels every concurrent terminal onto the one sticky account, which then hits Anthropic's per-account rate/concurrency limit (429) while other accounts sit idle. `acquireAccount()`/`releaseAccount()` layer **proactive load spreading** on top **without changing `getActiveAccount`** (so its warm-up / use-or-lose / recover behavior — and the tests that pin it — are untouched):

- Each account has `inflight` (in-flight count) and `maxConcurrent` (cap; `config.maxConcurrentPerAccount` default 3, per-account `maxConcurrent` override). `_tryAcquire` folds **capped** accounts into the exclude set and reuses `getActiveAccount(exclude)` to pick the best account *with a free slot* — filling A to its cap, then B, then C, by use-or-lose priority. JS is single-threaded so select→`inflight++` is race-free.
- When every available account is at its cap, `acquireAccount` **queues** the request (FIFO `_waiters`) up to `config.overflowQueueTimeoutMs` (default 15s); a `releaseAccount` drains waiters. Timeout → `null` → the client gets a `429`. If instead *no account is available at all* (quota-exhausted, not merely capped) it returns `null` immediately (no pointless wait). A queued request is **cancelled if the client disconnects** (an `AbortController` tied to `res` 'close' → `acquireAccount`'s `signal`) so it can't acquire a slot later and burn upstream quota for a response nobody is waiting for.
- **Memory bounds (localhost auth is skipped, so any local process could flood):** `server.js` enforces a global admission cap covering **every body-buffering path** (the proxied path *and* the `/v1/oauth/token` relay) — `inFlightProxied` may not exceed `accountManager.totalCapacity()` (sum of per-account caps + `overflowQueueMaxDepth` — 16, and `QUEUE_DEPTH_CEILING` clamps any configured value to that (logged once), so a larger number in a config is accepted-looking but inert) — and **rejects with `429` before buffering** the body. Per-request body size is capped by `config.maxRequestBytes` (default 32 MiB → `413`, enforced on the proxied path and inside `relayRaw`). Together they bound total buffered memory at roughly `totalCapacity × maxRequestBytes`.
- `forwardRequest` reserves a slot per attempt and releases it on completion (request `finally`) or before a failover recursion (`releaseHeld()`); a 401 same-account refresh-retry keeps the slot. `getStatus()` (and so `GET /teamclaude/status`) reports `inflight`/`maxConcurrent` per account — the **TUI does not render either**, so slot saturation is an HTTP-only diagnostic. `maxConcurrent` there is the *configured* cap; admission actually tests `inFlight < min(maxConcurrent, _rampCap(account))` and additionally refuses while `pausedUntil` is in the future, so an account can be at its effective limit with `inflight` below the reported number.
- **Connection affinity (prompt-cache locality):** `acquireAccount(..., affinityKey)` takes the client **socket** (`req.socket`) as a soft key. The first acquire on a connection remembers its account in a `WeakMap` (`_affinity`, value is the account *object* + an `accounts[i] === a` identity guard against a `removeAccount` re-index; GC'd when the socket closes); subsequent acquires on the same connection **prefer that account**. It's *soft* — honored only if that account is still available, has a free slot, and isn't `exclude`d, else it falls through to normal `_tryAcquire`. So HTTP/1.1 keep-alive (a session's **sequential** turns reuse one socket) keeps a terminal on one account (cache warm), while a **concurrent** burst — which necessarily opens separate sockets — still spreads by the cap logic. It never exceeds a cap or revives an exhausted account, so the 429 guarantees and use-or-lose for *new* connections are unchanged. It also **defers to cold-start warm-up** (skipped while any account is still a warm-up target) so it can't pin all of one connection's traffic to a single account and starve the others of quota data; only object/function keys are honored (a primitive key is ignored, never a `WeakMap` throw). This is also what blunts the periodic `reevalIntervalMs` re-prioritization — see the priority bullet above. **Caveat:** the key is the TCP socket, so "session" = connection. The normal case (one Claude Code process per terminal → its own connection) maps 1:1, but an intermediary that multiplexes *unrelated* logical sessions onto one keep-alive socket (e.g. a pooling agent with `maxSockets: 1`) would make them share an affinity and defer use-or-lose rotation until that account caps/exhausts — set `config.sessionAffinity: false` for such a front-end. Disabling routes purely by use-or-lose every request.

### Concurrency semantics & limits (what the cap is and isn't)

- The cap is on **concurrent in-flight requests per account, not "terminals."** A terminal is usually idle (waiting on the user / model), so it holds a slot only mid-request. `maxConcurrent: 3` means "≤3 requests upstream *at once* on this account," which is the right unit for burst rate-limiting — not a hard binding of 3 terminals to an account.
- **Spreading only kicks in on overflow.** While concurrent in-flight ≤ cap, traffic concentrates on the sticky primary (good for cache); other accounts stay idle until the primary is capped, then fill by use-or-lose. To spread *eagerly* across accounts, lower `maxConcurrentPerAccount` (e.g. `1`) at the cost of intra-account cache sharing.
- **The cap stops *burst / request-rate* 429s, not *quota-exhaustion* 429s.** A single large request can still exhaust an account's 5h/7d token quota with one slot in use; that path is handled separately (`isExhausted` → throttle the account + switch, in `forwardRequest`). Two complementary mechanisms — the cap is not a blanket 429 cure.
- **Caps are per-process.** Running two proxy instances against the same accounts does not share `inflight`, so combined concurrency can exceed the per-account intent. Single-proxy is the design assumption.

### Durable state across restarts (`<config>.state.v2.json`)

Quota lives only in memory, so a restart used to blank the whole dashboard (and blind use-or-lose ordering) until traffic organically re-measured every account. The server snapshots credential-free per-account quota/usage/throttle state, the active account, and the accepted probe template (`exportCanonicalState` in account-manager.js) into `<config>.state.v2.json` via `saveCanonicalState`/`loadCanonicalState` (config.js) — written every minute (unref'd interval) plus once more by an **awaited** `persistQuotaState()` inside `shutdown()` (SIGINT/SIGTERM/TUI quit; an exit that bypasses `shutdown()` — SIGKILL, uncaught throw — loses at most the last minute) — and restored at startup by `restoreCanonicalState`. Two older files are **read-only migration inputs, never written**: `<config>.state.json` and `<config>.quota.json` (consumed only when no v2 state loads). Restores are stale-safe: expired windows are lazily swept by `_isNearQuota`, a `throttle.until` in the past is not re-applied, and `error`/`exhausted` statuses have no field in the schema at all. Restored accounts count as measured, so warm-up doesn't re-probe them. Matching is by canonical `accountIdKey` (identity.js) **only** — no `accountUuid`/name guessing, unlike config sync.

**Trip-wire — the state schema is a strict allowlist enforced in BOTH directions.** `saveCanonicalState` validates before every write and `loadCanonicalState` validates on read. One unlisted field therefore makes *every* save throw — the only symptom is a `Failed to save canonical account state` line once a minute while the file silently freezes at its last valid write, and every restart then restores stale quota. The probe template is captured **verbatim from live traffic**, so upstream adding a request field can break saves with zero code changes on our side. Conversely, *narrowing* the allowlist can make the existing on-disk file unloadable at startup. So widen, never narrow: when the template shape or a quota field changes, extend the allowlists (`validateTemplateSystem` / the `*_FIELDS` sets in config.js) in the same commit, then confirm the file's `writtenAt` advances after a restart.

### Server lifecycle (status / stop / restart)

The running `server` writes a **state file** next to the config (`getServerStatePath()` → `<config>.server.json`: `{ pid, port, startedAt }`) on listen and removes it on exit (a SIGKILL leaves a stale file that the next command detects as dead and cleans up). `findRunningServer` probes candidate ports — the **state file's recorded port first** (it may differ from the current config port after an edit, and probing only the config port would miss → orphan the live server), then the config port — and accepts a port only if it answers a TeamClaude-shaped `/teamclaude/status` (a foreign process is *not* mistaken for ours → falls through to the EADDRINUSE message). The owning pid is resolved authoritatively via `lsof` (never a possibly-recycled state-file pid); the state-file pid is only a fallback when `lsof` is unavailable. The state file is cleared only when no candidate answers **and** its recorded pid is dead. `stop`/`restart` use this to SIGTERM→(wait)→SIGKILL the server, and `server` refuses to start a duplicate on an occupied port with a pointer to `stop`/`restart` instead of a raw bind error.

## The thing that's actually hard: config ⇄ memory synchronization

Most of the commit history is token-rotation/sync bug fixes. There are **three concurrent writers** to the config file:
1. The running server persisting refreshed OAuth tokens (`onTokenRefresh` callback in `index.js`).
2. The TUI's `saveConfig` (after import/add/remove).
3. External `teamclaude import`/`login` run while the server is up (picked up via TUI **R** / `syncAccountsFromDisk`).

Rules every config write must follow (see `atomicConfigUpdate`, `findConfigAccount`, `syncAccountsFromDisk`):
- **Always re-read disk before writing.** `atomicConfigUpdate(updater)` does this; never blind-`saveConfig` from a long-lived in-memory copy, or you clobber accounts added by another process.
- **Match accounts by `accountUuid` first, then by `name`.** Indexes shift; this matching is the dedup/sync key used everywhere.
- **Never overwrite fresher tokens with staler ones.** `syncAccountsFromDisk` compares `expiresAt` (`diskIsStaler`) before applying disk credentials over in-memory ones.
- Treat `AccountManager.accounts[i].credential/refreshToken/expiresAt` as the authoritative *live* tokens; the `config.accounts` array can lag.

Related gotcha: **`expiresAt` may arrive in seconds or milliseconds.** OAuth endpoints return seconds; Claude Code credentials use milliseconds. Always pass through `normalizeExpiresAt` (oauth.js) — assuming one unit was a recurring bug.

## Other intentional behaviors

- **`run`/`env` default to MITM forward-proxy mode** — they emit `HTTPS_PROXY`/`HTTP_PROXY` + `NODE_EXTRA_CA_CERTS` and *unset* `ANTHROPIC_BASE_URL` so the two modes don't stack in one shell; `--no-mitm` emits only `ANTHROPIC_BASE_URL` (see `src/claude-env.js`). Neither mode ever sets `ANTHROPIC_API_KEY` — loopback clients are exempt from the proxy key gate, and setting it would drop Claude Code out of subscription mode (full model access).
- **Account dedup** happens in `accounts` command and on every upsert: by `accountUuid`, keeping the most recently added.
- Token refresh is **coalesced** via `account._refreshPromise` so concurrent requests trigger one refresh — and **forced (post-401) refreshes are additionally floored** (`_lastRefreshAt`, 10s): the 401s from requests already in flight when a token rotated arrive *staggered*, so they slip past coalescing and would each rotate the refresh-token family (making the proxy the very "other holder rotating the family" that revokes shared credentials). A 401 for a just-minted token is stale news — the forced refresh is suppressed and the caller retries with the new token. Expiry-driven (`force=false`) refreshes are unaffected. A suppressed call returns `{ ok: true, suppressed: true }` so a caller that retries after a forced refresh (the usage prober) can skip a retry guaranteed to repeat the 401.
- **When a refresh parks an account** (`ensureTokenFresh`'s catch): only on a **genuine auth rejection** (`err.status` 400/401/403 — the refresh token is dead) or when the access token is **already expired** (nothing valid left to serve with). A transient failure (network/5xx/timeout) on a still-valid token must NOT park — `_isAvailable` excludes `error`, so a wrong park silently drops the account from rotation. Test expiry with `isTokenExpired`, never a raw `Date.now()` comparison (the `expiresAt` units gotcha above): a seconds-valued still-valid token read as expired parks on a blip, and the sweep — which normalizes — then sees a valid token and never attempts the heal.
- **Token keep-alive sweep** (`refreshLapsedTokens` in account-manager.js, wired on a timer in `serverCommand` — `config.tokenRefreshIntervalMs`, default 5 min, `0` = off, plus one immediate sweep at startup): periodically refreshes OAuth accounts whose access token is expiring/expired, **sequentially** (a fleet-wide lapse after downtime must not burst N concurrent POSTs at the token endpoint; overlapping sweeps are skipped via `_sweepInFlight`). Rationale: warm-up probes deliberately never refresh tokens and client traffic concentrates on the sticky account, so an idle account's refresh-token chain stops rotating and can be invalidated upstream. Parked (`error`) and disabled accounts are swept too — their chains must survive to be usable when they heal. **Error healing is cause-scoped** (`_errorFromRefresh`): a refresh-caused error (set by `ensureTokenFresh`'s catch) clears `error` → `active` on the next successful refresh — the thing that failed now succeeded; an error set by the *request path* (upstream 401 despite a fresh token at server.js's 401 handler, or a non-transient send failure) is **not** revived by a token-endpoint success (that would flap a rejected account back into rotation every sweep) — those heal only via `updateAccountTokens` (re-import/login) or a restart. The cause tag is set only on the error *transition*, so a later failed sweep refresh can't relabel an upstream-auth error as refresh-caused.
- Streaming responses must check `res.destroyed` to stop pulling from upstream when the client disconnects, and handle backpressure by racing `drain` against `close`.
- Log lines are prefixed `[TeamClaude]`; the TUI strips that prefix when mirroring `console.log`/`console.error` into its activity pane. Credentials are masked (sliced) in `--log-to` request dumps.
